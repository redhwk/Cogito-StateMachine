Created a PlayerResources "Container"
	1. Benefits of This Architecture
		- Single point of assignment: only one resource to manage in the inspector
		- Easy profile swapping: create multiple .tres files (e.g., "Fast Player", "Stealth Player", "Injured Player")
		- Runtime flexibility: use change_player_resources() to swap profiles based on:
			- Environmental factors (underwater, low gravity zones)
			- Player status (injured, power-ups, equipment changes)
			- Gameplay events (stealth mode, combat mode)
		- Cleaner code: no conditional logic for individual vs container resources
	2. Usage Example
		- In your game code, you can now easily swap player profiles:
			- var default_player_profile = preload("res://Scripts/Resources/PlayerProfiles/default_player_profile.tres")
			- var stealth_player_profile = preload("res://Scripts/Resources/PlayerProfiles/stealth_player_profile.tres")
		- Swap to default player
			- player_state_machine.change_player_resources(default_player_profile)
		- Swap to stealth player
			- player_state_machine.change_player_resources(stealth_player_profile)

How it works
When a state emits finished.emit("Grounded"):
	StateMachine transitions to Grounded parent
	Grounded.enter() is called
	Grounded immediately emits finished.emit("Idle")
	StateMachine transitions to Idle
	Player is now in Idle state
The state machine supports:
	Multi-tier hierarchies (StateMachine → Grounded → Idle)
	Parent state auto-transitions
	Direct child state transitions ("Idle", "Walk", etc.)
	Parent state transitions ("Grounded", "Airborne", "Climbing")
